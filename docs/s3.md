# Amazon S3 and Glacier

Amazon S3 is a cloud object store run by Amazon Web Services (AWS). Data that is rarely needed can be kept in the Glacier storage classes, which cost less to store. Most of them cannot be read until the data is restored.

This page covers the basic ideas, how to list what is in S3, how to restore archived objects, and how to copy objects from S3 to a local file system.

## Prerequisites

- Familiarity with the Linux command line
- The [AWS command line interface](https://aws.amazon.com/cli/) (version 2) installed and on your `PATH`
- Working AWS credentials with access to the buckets you need

Installing the AWS command line interface and setting up authentication are outside the scope of this page. To check that both work, run:

```bash
aws sts get-caller-identity
```

This prints the account and identity your credentials belong to. Then check that you can read S3:

```bash
aws s3 ls
```

This lists the buckets you can see. Some accounts do not allow listing all buckets. In that case, try a bucket you know you have access to:

```bash
aws s3 ls s3://BUCKET/
```

If these commands fail, ask whoever manages your AWS access for help.

## Concepts

### Buckets, keys, and URIs

S3 stores **objects** (files) in **buckets**. Each object has a **key**, its name within the bucket. Keys often contain slashes, which makes them look like file paths, but S3 has no real directories. A **prefix** is the leading part of a key, such as `project1/run5/`, and the AWS tools treat a prefix ending in `/` as if it were a directory.

An object is identified by an S3 URI:

```
s3://BUCKET/KEY
```

For example, `s3://example-bucket/project1/run5/sample_001.cram` is the object with key `project1/run5/sample_001.cram` in the bucket `example-bucket`.

### Storage classes

Every object has a storage class. For practical purposes there are two kinds:

| Storage class | Readable immediately? | Typical use |
|---|---|---|
| `STANDARD`, `STANDARD_IA`, `INTELLIGENT_TIERING`, `GLACIER_IR`, and all others | Yes, except `INTELLIGENT_TIERING` objects in an archive tier (see below) | Active data |
| `GLACIER`, `DEEP_ARCHIVE` | No, must be restored first | Archived data |

Objects in the `GLACIER` and `DEEP_ARCHIVE` classes appear in listings with their full name and size, but they cannot be copied until they have been restored.

`INTELLIGENT_TIERING` has optional Archive Access and Deep Archive Access tiers. If a bucket enables them, objects that move into those tiers must be restored before they can be read, even though their storage class is still `INTELLIGENT_TIERING`. `aws s3api head-object` shows the tier in an `ArchiveStatus` field.

### Restores

A restore of a `GLACIER` or `DEEP_ARCHIVE` object creates a temporary readable copy for a number of days that you choose. The archived object stays in Glacier the whole time. A restore of an archived `INTELLIGENT_TIERING` object instead moves the object back to a readable tier, with no expiry. Most restores take hours, and a `DEEP_ARCHIVE` restore can take up to two days. Once the restore completes, copy the object before the temporary copy expires.

Restores usually cost money: there is a request charge, there is often a retrieval charge, and for `GLACIER` and `DEEP_ARCHIVE` you pay to store the temporary copy while it exists. `Bulk` restores from `GLACIER`, and `Standard` and `Bulk` restores from Intelligent-Tiering, have no retrieval charge.

## Finding Objects

The [AWS Object Search](aws-object-search.md) tools search an index of bucket contents by name. Their output includes each object's storage class, which tells you whether it may need a restore. The storage class is the one recorded when the index was last updated, so an object archived since then still shows its old class. To be sure, check the current class with `aws s3api` as shown in [Listing the Contents of a Bucket](#listing-the-contents-of-a-bucket). An `INTELLIGENT_TIERING` object in an archive tier looks the same as one that is readable; see [Restoring Intelligent-Tiering objects](#restoring-intelligent-tiering-objects).

## Listing the Contents of a Bucket

List a bucket's top level:

```bash
aws s3 ls s3://BUCKET/
```

List the contents of a prefix:

```bash
aws s3 ls s3://BUCKET/PREFIX/
```

The trailing `/` matters. Without it, `aws s3 ls` lists the objects and prefixes at that level whose names start with the text you gave, without descending into them. With it, the command lists the contents of that "directory". Lines marked `PRE` are prefixes, which you can list in turn.

List every object under a prefix, at any depth, and show a total at the end:

```bash
aws s3 ls s3://BUCKET/PREFIX/ --recursive --human-readable --summarize
```

`aws s3 ls` does not show storage classes. To list the key and storage class of every object under a prefix:

```bash
aws s3api list-objects-v2 --bucket BUCKET --prefix PREFIX/ \
    --query 'Contents[].[Key,StorageClass]' --output text
```

To check one object, see [Checking a restore](#checking-a-restore).

## Restoring Glacier Objects

Some accounts allow only certain people to run restores. If the command below fails with an access error, ask whoever manages your AWS access to run the restore for you.

### Starting a restore

Restore one object and keep the temporary copy for 7 days:

```bash
aws s3api restore-object --bucket BUCKET --key KEY \
    --restore-request '{"Days": 7, "GlacierJobParameters": {"Tier": "Standard"}}'
```

The `Tier` controls speed and cost:

| Tier | `GLACIER` | `DEEP_ARCHIVE` |
|---|---|---|
| `Expedited` | Minutes, highest cost | Not available |
| `Standard` | About 3 to 5 hours | Within about 12 hours |
| `Bulk` | About 5 to 12 hours, no retrieval charge | Within about 48 hours, lowest cost |

`Expedited` requests can be refused when demand is high. If that happens, use `Standard`.

To restore many objects, put one key per line in a file. This writes the keys of all `GLACIER` and `DEEP_ARCHIVE` objects under a prefix to `keys.txt`:

```bash
aws s3api list-objects-v2 --bucket BUCKET --prefix PREFIX/ \
    --query "Contents[?StorageClass=='GLACIER' || StorageClass=='DEEP_ARCHIVE'].[Key]" \
    --output text > keys.txt
```

If the prefix holds no objects at all, the command writes the single word `None` instead of an empty file. Check `keys.txt` before going on.

If you found the objects with [AWS Object Search](aws-object-search.md), build `keys.txt` from its output instead. Its first column is an S3 URI and its fourth is the storage class. This keeps the `GLACIER` and `DEEP_ARCHIVE` objects in one bucket and strips `s3://BUCKET/` to leave the key:

```bash
awk -F'\t' '$4 == "GLACIER" || $4 == "DEEP_ARCHIVE" {print $1}' RESULTS.tsv \
    | sed -n 's|^s3://BUCKET/||p' | sort -u > keys.txt
```

`RESULTS.tsv` is the `.out.tsv` file from `search.py`, or saved output from `search-aws`, produced without `--uri-only`. If the results span several buckets, run it once per bucket, writing each to its own file such as `keys-BUCKET.txt` in place of `keys.txt`, and run the restore loop below once for each file with its bucket. `sort -u` removes duplicates, since `search.py` lists an object once for each search term it matches.

The search output cannot tell you which `INTELLIGENT_TIERING` objects are archived, so this command skips them. To find those, see [Restoring Intelligent-Tiering objects](#restoring-intelligent-tiering-objects).

Then loop over the file:

```bash
while IFS= read -r key; do
    aws s3api restore-object --bucket BUCKET --key "$key" \
        --restore-request '{"Days": 7, "GlacierJobParameters": {"Tier": "Bulk"}}'
done < keys.txt
```

Running the loop again is safe. An object whose restore is still in progress fails with a `RestoreAlreadyInProgress` error, which you can ignore. An object that is already restored has its expiry reset to the new number of days, counted from now. Each run is billed as new restore requests, and extending a restore adds to the cost of storing the temporary copy.

### Restoring Intelligent-Tiering objects

Objects in the Intelligent-Tiering archive tiers do not accept `Days`. Give an empty restore request instead:

```bash
aws s3api restore-object --bucket BUCKET --key KEY --restore-request '{}'
```

This uses the `Standard` tier. To choose another, use `--restore-request '{"GlacierJobParameters": {"Tier": "Bulk"}}'`. Restore times follow the table above, with Archive Access matching `GLACIER` and Deep Archive Access matching `DEEP_ARCHIVE`. `Expedited` is available for Archive Access but not for Deep Archive Access.

A bucket listing shows archived Intelligent-Tiering objects as plain `INTELLIGENT_TIERING`, so the `keys.txt` command above does not find them. To find them, list the Intelligent-Tiering keys under a prefix, then check each one with `head-object` and keep those that have an `ArchiveStatus`:

```bash
aws s3api list-objects-v2 --bucket BUCKET --prefix PREFIX/ \
    --query "Contents[?StorageClass=='INTELLIGENT_TIERING'].[Key]" \
    --output text > it-keys.txt
while IFS= read -r key; do
    status=$(aws s3api head-object --bucket BUCKET --key "$key" \
        --query ArchiveStatus --output text)
    if [ -n "$status" ] && [ "$status" != "None" ]; then
        printf '%s\n' "$key"
    fi
done < it-keys.txt > it-archived.txt
```

As with `keys.txt`, if the prefix holds no objects at all, `it-keys.txt` contains the single word `None`. Check it before running the loop.

This makes one request per object, so it is slow for large prefixes. A key whose check fails is left out of `it-archived.txt`, so if the loop prints any errors, fix the cause and run it again. Then restore the keys in `it-archived.txt`:

```bash
while IFS= read -r key; do
    aws s3api restore-object --bucket BUCKET --key "$key" --restore-request '{}'
done < it-archived.txt
```

Running this loop again may print errors for objects that are already restored or still being restored; you can ignore them.

### Checking a restore

```bash
aws s3api head-object --bucket BUCKET --key KEY
```

The output includes `StorageClass` (omitted for `STANDARD` objects) and, once a restore has been requested, a `Restore` field:

- `ongoing-request="true"` means the restore is still in progress.
- `ongoing-request="false", expiry-date="..."` means the object is readable until the expiry date.

A restored Intelligent-Tiering object has no expiry date. It is readable once the output no longer has an `ArchiveStatus` field.

To check every key in `keys.txt`, printing each key with its `Restore` field:

```bash
while IFS= read -r key; do
    restore=$(aws s3api head-object --bucket BUCKET --key "$key" \
        --query Restore --output text)
    printf '%s\t%s\n' "$key" "$restore"
done < keys.txt
```

A key showing `None` has no restore requested, or its restore has expired. A key showing nothing could not be checked, for example because it does not exist or you lack access; the error is printed above it.

This loop is meant for `GLACIER` and `DEEP_ARCHIVE` keys. For Intelligent-Tiering keys such as those in `it-archived.txt`, the `Restore` field is not a reliable guide. Instead, rerun the `ArchiveStatus` loop above, reading `it-archived.txt` in place of `it-keys.txt` and writing `it-still-archived.txt` in place of `it-archived.txt`, so the list of restored keys is kept. If the loop prints no errors, a key missing from `it-still-archived.txt` is readable.

## Copying from S3 to a Local File System

Run large copies on a host with fast access to the destination storage, and check that the destination has enough free space first.

Copy a single object into a directory:

```bash
aws s3 cp s3://BUCKET/PATH/TO/FILE /PATH/TO/DIRECTORY/
```

Copy everything under a prefix into a directory:

```bash
aws s3 cp s3://BUCKET/PREFIX/ /PATH/TO/DIRECTORY/ --recursive
```

### Copying restored Glacier objects

The AWS command line interface does not copy an archived object that has not been restored. It prints a warning, skips the object, and exits with a non-zero status:

```
warning: Skipping file s3://BUCKET/KEY. Object is of storage class GLACIER. Unable to perform download operations on GLACIER objects. ...
```

The message says `GLACIER` for `DEEP_ARCHIVE` objects too. Because it is only a warning, a large copy can finish with some objects missing, so check the output for these lines.

Archived `INTELLIGENT_TIERING` objects are not skipped. The command tries to download them and fails with an `InvalidObjectState` error, so check the output for those errors too.

A single restored object copies normally. A `--recursive` copy skips Glacier objects even after they are restored, because it does not check each object's restore status. Add `--force-glacier-transfer` to copy them:

```bash
aws s3 cp s3://BUCKET/PREFIX/ /PATH/TO/DIRECTORY/ --recursive --force-glacier-transfer
```

`--force-glacier-transfer` does not replace the restore. It only tells the command to attempt the download, so any object under the prefix that has not been restored fails with an error instead of being skipped.
